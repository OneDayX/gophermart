# Гофермарт — накопительная система лояльности

Дипломный проект курса «Go-разработчик» Яндекс Практикума. Техническое задание — в [SPECIFICATION.md](SPECIFICATION.md).

Сервис — HTTP API, в котором пользователь регистрируется, загружает номера своих заказов, получает за них баллы от внешней системы расчёта начислений (accrual) и тратит баллы на оплату новых заказов.

## API

| Метод и путь | Назначение | Коды ответа |
|---|---|---|
| `POST /api/user/register` | регистрация и сразу аутентификация | 200, 400, 409, 500 |
| `POST /api/user/login` | аутентификация | 200, 400, 401, 500 |
| `POST /api/user/orders` | загрузка номера заказа (`text/plain`) | 200, 202, 400, 401, 409, 422, 500 |
| `GET /api/user/orders` | заказы пользователя, новые первыми | 200, 204, 401, 500 |
| `GET /api/user/balance` | текущий баланс и сумма списаний | 200, 401, 500 |
| `POST /api/user/balance/withdraw` | списание баллов в счёт заказа | 200, 400, 401, 402, 422, 500 |
| `GET /api/user/withdrawals` | списания пользователя, новые первыми | 200, 204, 401, 500 |

Токен выдаётся при регистрации и входе сразу двумя способами: в заголовке `Authorization: Bearer <token>` и в cookie `token`. Защищённые хендлеры принимают любой из них. Запросы и ответы можно сжимать gzip.

## Запуск

```sh
make build
./cmd/gophermart/gophermart -a localhost:8090 -d 'postgres://…' -r http://localhost:8091
```

| Флаг | Переменная окружения | Назначение | По умолчанию |
|---|---|---|---|
| `-a` | `RUN_ADDRESS` | адрес и порт сервиса | `localhost:8080` |
| `-d` | `DATABASE_URI` | строка подключения к PostgreSQL | обязателен |
| `-r` | `ACCRUAL_SYSTEM_ADDRESS` | адрес системы расчёта начислений; без схемы подставляется `http://` | обязателен |
| `-k` | `AUTH_KEY` | ключ подписи токенов | случайный при каждом запуске |

Переменная окружения важнее флага. Без `AUTH_KEY` токены перестают действовать после перезапуска, об этом пишется предупреждение в лог. Миграции схемы встроены в бинарник и применяются при старте.

Локально удобнее через Makefile (нужен Docker для PostgreSQL):

```sh
make accrual   # в отдельном терминале: система расчёта из шаблона на порту 8091
make run       # поднимает postgres в Docker и запускает сервис на порту 8090
```

`make help` показывает все цели.

## Тесты

```sh
make test      # юнит-тесты с -race; тесты с БД пропускаются
make test-db   # все тесты, включая интеграционные с PostgreSQL
make cover     # общее покрытие по всем пакетам
make autotest  # автотесты Практикума gophermarttest, как в CI
```

Тесты с базой запускаются, когда задана переменная `TEST_DATABASE_DSN`, и перед каждым тестом очищают таблицы. Пакеты с такими тестами пользуются одной базой, поэтому `make test-db` гоняет пакеты по очереди (`-p 1`).

- **Репозитории** проверяются на настоящей базе.
- **Приложение целиком** (`internal/app`) проверяется сквозным тестом: регистрация, загрузка заказа, начисление от фейковой системы accrual и списание.
- **Остальные пакеты** покрыты юнит-тестами на заглушках.

Покрытие по `make cover`: около 85% с базой, около 65% без неё.

Для `make autotest` бинарник `gophermarttest` нужно скачать из [релизов go-autotests](https://github.com/Yandex-Practicum/go-autotests/releases) и положить в `PATH`.

## Устройство

```
cmd/gophermart          точка входа: конфигурация, логгер, сигналы
internal/app            сборка компонентов, роутер, запуск и graceful shutdown
internal/handler        HTTP-хендлеры: разбор запросов, коды ответов
internal/server/middleware  логирование, gzip, проверка токена
internal/service        бизнес-правила: регистрация, заказы, списания
internal/repository     работа с PostgreSQL
internal/worker         опрос системы расчёта начислений
internal/accrual        HTTP-клиент системы расчёта начислений
internal/auth           JWT, bcrypt, пользователь в контексте запроса
internal/luhn           проверка номера по алгоритму Луна
internal/config         флаги и переменные окружения
internal/database       пул соединений и миграции
internal/models         сущности и общие ошибки
migrations              SQL-миграции, встроенные через embed
```

Слои связаны через маленькие интерфейсы, объявленные на стороне потребителя. Ошибки предметной области — sentinel-значения из `models`, хендлеры переводят их в HTTP-коды через `errors.Is`.

### Ключевые решения

- **Деньги.** Баллы хранятся в `numeric`, а вся арифметика (начисление, списание, проверка остатка) выполняется в SQL. В Go суммы только передаются между JSON и базой, поэтому ошибки округления `float64` не накапливаются.
- **Списание без гонок.** Баланс хранится в строке пользователя. Проверка остатка и списание — один условный `UPDATE … WHERE balance >= $sum` в транзакции вместе с записью в `withdrawals`. Из двух параллельных списаний второе ждёт блокировку строки и видит уже уменьшенный баланс. `CHECK (balance >= 0)` страхует на уровне схемы.
- **Идемпотентное начисление.** Заказ в финальном статусе (`INVALID`, `PROCESSED`) не обновляется. Повторный или параллельный ответ accrual не начислит баллы второй раз.
- **Уникальность номеров.** Гонку двух загрузок одного номера разрешает первичный ключ (`ON CONFLICT DO NOTHING`), а не проверка перед вставкой. Затем по владельцу строки выбирается ответ 200 или 409.
- **Опрос accrual.** Раз в секунду воркер берёт пачку заказов в статусах `NEW` и `PROCESSING`: сначала те, о которых дольше всего не спрашивал. Пачка проверяется через `errgroup` с `SetLimit`, не больше четырёх заказов одновременно. На 429 остаток пачки отменяется, и воркер замолкает на время из `Retry-After` (секунды или HTTP-дата, по умолчанию 60 с, не больше часа).
- **Незарегистрированные заказы.** Если accrual ещё не знает заказ (204), тот остаётся `NEW` и опрашивается снова, так как регистрация может произойти позже. Прерванная при остановке проверка просто повторится после запуска.
- **Авторизация.** JWT HS256 со сроком 24 часа. Алгоритм зафиксирован при проверке, поэтому токен с `alg: none` или чужим алгоритмом не пройдёт. Пароли хешируются bcrypt; длина пароля ограничена 72 байтами — пределом bcrypt.
- **Логи.** Логгер запросов пишет метод, путь, статус, размер и время ответа, но не тела запросов: в них пароли.
